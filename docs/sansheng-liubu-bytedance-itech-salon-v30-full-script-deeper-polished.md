## Slide 2 先把边界说清楚

先声明边界。今天不是产品发布，也不是“我已经做出一个成熟生产平台”。三省六部现在还在持续改造中，有些地方已经跑通，有些地方还是规则版 MVP，有些地方还只是路线图。

所以今天更准确的定位是：一个个人项目在工程化过程中遇到的问题，以及我怎么把这些问题重新抽象成控制面、策略、证据链和接管机制。

我希望大家听完以后，不一定认同我的方案，但至少可以一起讨论三个问题：

第一，当 Agent 能操作真实资源时，我们凭什么信任它？

第二，当它卡住或失败时，我们怎么定位？

第三，当它越界或不确定时，人怎么接管？

这三个问题，比“再接一个更强的模型”更接近企业落地。

很多事故最可怕的不是“系统错了”，而是复盘时大家一起看日志，最后只剩下三句话：谁干的？什么时候干的？能不能回滚？如果这三个问题答不上来，模型再聪明，也很难放心让它进生产流程。

这里也先给大家打个预防针：我会有一点自嘲和工作场景，但不会讲成吐槽大会。技术分享里最好的笑点，不是让大家忘掉技术，而是让大家更快记住技术判断。

## Slide 3 核心论点

这一页先把核心判断讲清楚：执行能力越强，控制面越关键。

过去我们讲 AI，更多是问答。答错了，最多重新问一遍。后来我们讲 Agent，它开始调工具、读文件、执行命令、改代码。这个时候问题变了：它不是说错一句话，而是可能真的在你的电脑、仓库、文档里做了事。

问答模型答错了，有点像同事在群里发了一个不太准确的结论，你可以补一句“这个再确认一下”。但 Agent 如果拿着权限去执行，性质就变了。它不是在群里发言，它是已经拿着门禁卡去机房了。

这个时候你不能只说“它主观上是善意的”。工程里最怕的不是主观恶意，是主观善意加上客观权限。

所以我把 Agent 平台的生产化门槛总结成三个词：Trust、Monitor、Takeover。

Trust 是信任，不是盲目信任，而是我知道它为什么这么做、用了什么工具、改了什么东西。

Monitor 是可观测，不是看到一堆日志，而是能快速知道任务现在卡在哪一层，是模型、队列、权限、工具，还是工作区。

Takeover 是可接管，不是等它跑飞以后再祈祷，而是在危险动作前能审批，在失败后能降级，在不确定时能停下来。

三省六部想做的，就是在执行型 Agent 外面补一层运行治理层。后面三个本地案例不是要“证明已经生产落地”，而是说明这条闭环已经开始跑起来。

## Slide 5 起源：从任务可视化开始

我最开始真没想这么大。

当时我看到一些终端型 Agent，尤其是复杂任务时，交互比较偏程序员：命令行、日志、模型回复、工具调用混在一起。对熟悉终端的人，这没问题；但对于一个想管理多个任务、多个模型、多个 Agent 的人，它不够像一个工作台。

所以最早的想法很简单：能不能做一个更好看的页面？至少让人知道任务在哪里、谁在处理、下一步是什么。

这个起点非常像很多个人项目：一开始只是想“我就改个 UI”。这句话在工程里非常危险，跟“我就顺手改一行代码”差不多。你以为你在换皮肤，最后发现后面连着状态机、队列、权限、模型路由和一整套祖传逻辑。

---

## Slide 6 真正缺的不是一个页面

这一页是转折。

我这里不是批评 OpenCode。更准确地说，OpenCode 是以 coding/runtime 为主的执行 surface，它覆盖开发者会话、模型选择、读仓库、跑命令、改文件等能力。对程序员来说，它非常直接，也很强。

但继续做下去，我发现最初的问题看起来像 UI，实际是在问另一件事：当任务变多、会话变长、模型变多、执行路径变复杂之后，只靠单次会话视角，很难回答几个问题。

这个任务现在到底谁在做？它卡住了吗，还是只是慢？它用了哪个模型，模型是不是超时？它有没有改文件，产物在哪里？我想接管，应该从哪里接？

这就像公司里一个项目，如果只有群聊，没有需求文档、没有 owner、没有验收标准、没有上线记录。每天群里都很热闹，消息刷得像过年，但你问“这个需求现在到哪了”，大家会突然变得很安静。

所以这一页的转折是：真正缺的不是一个页面，而是跨任务治理、过程证据和交付物视图。

## Slide 7 为什么三省六部能传播

三省六部这个名字为什么能传播？我觉得不只是因为历史感，也不是因为大家都想当皇帝。

虽然说实话，“下旨”这个按钮确实有一点情绪价值。以前点按钮叫提交，现在叫下旨，感觉工单都变得有仪式感了。

但你不能真的以为点了“下旨”，任务就会像古装剧一样自动跪下说“臣已办妥”。现实更像企业协作：你下旨之后，它可能先问你预算、权限、排期和验收口径。AI 时代了，流程还是没放过我们。

三省六部真正的价值，是降低理解成本。

很多 Agent 框架一上来讲 planner、executor、tool call、memory、DAG、handoff。技术上没问题，但普通用户很难马上建立心智。

三省六部用一个大家熟悉的治理隐喻，把复杂协作拆成责任边界。

太子负责意图分拣，中书省负责起草 RunSpec，门下省负责审议和拦截，尚书省负责派发，六部负责具体执行，回奏负责结果归档。

这里要强调一句：角色不是 cosplay，不是每个角色都必须是一个独立大模型。它们更像工程对象。有的角色是规则，有的角色是状态机，有的角色是 UI，有的角色是 Agent，有的角色只是事件记录。

隐喻的价值不是好玩，而是让复杂系统能被讨论。

## Slide 8 第一版的问题

第一版解决了入口，但没有解决运行治理。

当项目传播以后，我才意识到，用户不是只想看一个漂亮面板。用户会问：为什么太子不派发？为什么任务完成了但状态没变？为什么 OpenCode 里有模型，三省六部模型注册表里没有？为什么派发失败以后我不知道失败在哪？为什么输出文件还要自己去找？

这些问题听起来像 UI 问题，但底层其实是工程问题。

第一版有点像把会议室装修得特别漂亮，大屏也装了，灯光也调了，结果一开会发现没有议程、没有纪要、没有负责人。唯一确定的事情是：会议室确实挺好看。

任务会卡住，是因为状态机、队列和执行 session 没有完全绑定。

信息混乱，是因为 flow、progress、tool、model、artifact 混在一起，没有分层。

模型不可控，是因为 OpenCode 已配置模型还没同步成平台自己的模型注册表，也没有健康检查、延迟观测和降级策略。

权限风险，是因为 UI 可以提示风险，但执行层还没有强策略闸门。

所以这次大改版的核心，不是把页面变漂亮，而是把任务变成一个可治理、可观测、可接管的对象。

## Slide 9 踩过的坑：Session 活着，不等于任务能跑

这一页是我专门加的失败案例，因为我不希望整场分享听起来像“我一路都想对了”。真实情况是，三省六部第一版最大的问题，很多都是运行时把我按在地上教育出来的。

有一次最典型的现象是：看板上看起来任务卡住，派发失败，错误里出现 `Session not found`。这时候如果只看页面，很容易以为是某个 Agent 不努力，或者模型没响应。

但真正往下查，会发现问题更复杂：进程健康不等于会话健康，OpenCode 或执行 Runtime 还活着，不代表它内部 session 还可用；旧 outbox、旧模型健康记录、旧失败状态也可能污染当前判断。

这件事给我的教训很直接：可观测性不是多放日志，而是让当前堵点浮上来。

所以后面我开始把 task_id、trace_id、session、runtime outbox 串起来，同时区分真实失败和历史噪声。否则你以为自己在做智能 Agent，其实是在做“猜谜面板”。

这页的转场也很自然：第一版的问题不是“不够好看”，而是缺少把任务变成可治理对象的控制面。
## Slide 10 大改版

如果说第一版是“给 Agent 做一个看板”，那新版更像“给 Agent 做一个控制面”。

我现在回头看，第一版更像“老板大屏”：很炫，适合远看；新版更像“值班台”：不一定每一秒都漂亮，但你真出问题的时候，它得告诉你哪里堵了、谁在跑、下一步该怎么救。

控制面这个词在基础设施里很常见。数据面负责实际流量，控制面负责策略、路由、配置、观测和调度。

放到 Agent 里，我的理解是：Runtime 负责真正执行，比如调模型、调工具、写文件；控制面负责在执行之前、执行之中、执行之后，回答边界和证据问题。

执行前：这是什么任务，需要什么能力，风险多高，是否需要审批。

执行中：它在哪个阶段，队列是否堵，模型是否超时，有没有证据。

执行后：产物在哪，是否通过校验，能不能回滚，经验能不能沉淀。

## Slide 11 Control Spine

这一页是新版的 Control Spine：自然语言请求，先变成 RunSpec，再进 Policy Gate，再到 Runtime，最后回到 Evidence。

RunSpec 可以理解成任务合同。用户说一句话，系统不能直接把这句话丢给模型执行，而是先整理出目标、交付物、约束、能力、风险、审批、执行图。

“把系统优化一下”这句话，在工程里属于经典高危自然语言。它看起来只有七个字，展开以后可能是三个月、五个团队、八次评审，最后上线那天大家在群里整齐回复“辛苦了”。

所以 RunSpec 的意义，就是先把这七个字拆成人能验收、系统能执行、出事能回滚的任务合同。

但我也知道，这一页一定会被技术同学追问：RunSpec 是怎么来的？是不是硬编码？泛化怎么办？所以我不把这个问题藏到 Q&A，下一页先说清楚。

---

## Slide 12 RunSpec：规则不是大脑，是安全脚手架

这一页专门回答 RunSpec 的来源问题。

我不回避，当前 V0 里确实有规则、模板和能力配置。比如某类任务需要 shell.command，某些词会触发高风险，某些模式会进入 read-only 或 plan-first。

这个东西如果被包装成“我们已经能理解任意自然语言并自动规划”，那一定会被批评，而且批评得很对。

但我的真实设计不是这样。

RunSpec 是任务合约，里面包含权限、风险、终止条件和输出契约。安全相关字段不能一开始完全交给模型自由决定。模型可以提议，schema 要校验，policy 要裁决，高风险和低置信度要进 human preview。

所以这里的规则不是最终智能，而是 bootstrap compiler。它先覆盖高频、低歧义、可测试的任务类型，让系统有可解释、可回放、可审计的最小闭环。

后续怎么演进？不是让硬编码越来越厚，而是把它拆成四层：

第一，LLM 或规则生成候选意图；第二，Schema Validator 做字段完整性和冲突检查；第三，Policy Overlay 用 tool allowlist、scope、resource、action 做风险取高；第四，高风险、低置信度、字段冲突进入 Human Preview。

这里可以轻松一点说：生产权限最好不要靠“模型感觉可以”。公司里有些事情可以靠感觉，比如中午吃什么；但生产环境和 shell 权限最好别靠感觉。

## Slide 13 OpenCode 与三省六部的关系

这一页要特别谨慎，因为现场可能有人比我更熟 OpenCode。

我不是说 OpenCode 没有治理能力，也不是说 OpenCode 不够强。OpenCode 这类执行型 Agent 本身已经有 runtime 或 session 层面的权限、计划模式、策略配置和会话控制。

我的表达是：在三省六部这个项目里，我把 OpenCode 当作执行面来接入；三省六部补的是任务级控制面。

OpenCode、Claude Code 这类工具很强，它们解决的是开发者会话里的执行问题：怎么调模型、怎么读仓库、怎么跑命令、怎么改文件、怎么快速推进一个任务。

三省六部不是要替代它，也不是要和执行型 Agent 抢活。它解决的是 Control Plane 问题：目标怎么变成任务对象，谁批准，用什么权限，任务卡在哪里，产物在哪里，证据怎么留，什么时候该人接管。

打个比方，OpenCode 是发动机，三省六部不是再造发动机，而是补仪表盘、刹车、行车记录和调度规则。发动机越强，仪表盘和刹车越不能省。否则你不是开车，是许愿。

单人、低风险、临时探索，直接用执行型 Agent 就很好。比如我自己改一个脚本、跑一个实验、总结一个仓库，这时加控制面可能反而啰嗦。

但如果是多任务、跨会话、需要审计、需要隔离、需要审批、需要回滚的场景，就不能只看一次会话里模型说了什么，而要把它提升成一个任务对象。

---

## Slide 14 不是竞品，是上下两层

这页继续把边界讲实。

如果只是低风险、单人、临时探索，OpenCode 或 Claude Code 很好。比如解释一段代码、改一个小工具、跑一个本地测试，这时候它的优势是单会话推进直接、启动成本低。

但如果进入组织场景，问题会变成另一种：谁发起的任务？有没有审批？用了什么权限？有没有操作敏感文件？产物在哪里？失败了怎么回滚？下次怎么复盘？

这些不是“模型再聪明一点”就自动解决的。

所以这页分三层：

第一层是执行面 Runtime，以 coding/runtime 为主，负责读仓库、跑命令、改文件、调模型。

第二层是三省六部这样的任务级 Control Plane，负责 RunSpec、Policy Gate、Queue、Trace、Evidence。

第三层是企业 IT 和平台治理，负责审批人、组织策略、敏感数据分级、SLO 和审计留存。

我最想让大家记住的边界是：执行型 Agent 解决“能执行”，三省六部解决“敢放权”。

能干活是一回事，敢不敢把活交给它，是另一回事。

## Slide 15 控制面全貌

这一页信息量比较大，现场不用逐字读。只看三条线。

第一条是治理线：Goal → RunSpec → Policy。它回答“这个任务是什么、边界在哪里、能不能执行”。

第二条是执行线：Orchestrator → Runtime → Tools。它回答“谁去干、用什么工具干、在哪个环境干”。

第三条是证据线：Trace → Evidence → Monitoring。它回答“干了什么、证据在哪、出了问题怎么复盘”。

这页右上角我也加了状态说明：已跑通、原型中、路线图。这个很重要，因为我不希望大家把这张图理解成“成熟度承诺”。颜色表示职责，不表示成熟度。

这里最怕的是把治理关系和执行关系混在一起。混在一起以后，看起来很热闹，实际上没人负责。

这在公司协作里也很常见：群很多，会很多，同步很多，最后真正需要拍板的时候，大家都在等“上一个环节”。系统架构如果也是这样，Agent 之间互相 handoff，handoff 到最后就像传文件，文件名从“最终版”变成“最终版_真的最终_周三确认版”。

三省六部要避免的就是这种状态：每一步可以复杂，但责任边界必须清楚。

下一步问题是：如果控制面这么重要，那是不是 Agent 越多越好？答案是否定的。

## Slide 16 主流 Agent 架构

这部分不是说三省六部比别人高级，而是把它放回主流 Agent 工程脉络里看。

今天很多 Agent 框架都在朝几个方向收敛：工具调用、handoff、workflow、tracing、guardrails、human-in-the-loop、evals。

我的做法是把这些工程对象，用三省六部的隐喻重新组织起来。

所以这一部分只回答三个问题：

第一，什么时候用更简单的机制就够了？

第二，什么时候才需要 Multi-Agent？

第三，三省六部为什么选择治理星型 + 执行网络？

---

## Slide 17 生态位：不是替代协议，而是补任务控制面

这一页是为了避免另一个误解：三省六部不是想替代 MCP、A2A、Agents SDK 或 LangGraph。

MCP 更像工具和上下文连接层，它解决模型怎么连接外部工具、数据和系统。

A2A 更像 Agent 互操作层，它讨论 Agent 之间怎么发现、通信和协作。

OpenAI Agents SDK、LangGraph 这类框架，更偏编排与运行层，强调 tracing、guardrails、handoff、human-in-the-loop、persistence 这些工程能力。

OpenCode、Claude Code 这类工具，则更偏执行面 Runtime，尤其是 coding/runtime 场景：读仓库、跑命令、改文件、调模型。

三省六部的位置不是替代它们，而是把这些能力收敛到一个任务控制面里：RunSpec、Policy、Queue、Trace、Evidence、Takeover。

一句话概括：MCP 接工具，A2A 接 Agent，三省六部关心“这个任务能不能被组织放心交出去”。

这页也给后面多 Agent 段落做铺垫：既然生态里已经有很多层，那什么时候该用简单工具，什么时候才该上多 Agent？
## Slide 18 Skill or Team

能用工具、技能包、workflow 解决的，先不要急着多 Agent。

我现在更倾向于一个原则：先用更简单的机制，必要时再上多 Agent。自由协作不是默认选项。

因为多 Agent 不是免费午餐。每多一个 Agent，就多一个上下文边界、多一次 handoff、多一个失败点、多一份观测成本。

公司里最可怕的会议不一定是没人来，而是所有人都来了，但没人知道自己为什么来。多 Agent 也是一样，不是把角色拉满就叫智能，有时候只是把问题从“一个模型想不明白”，升级成“六个模型一起想不明白”。

所以三省六部不是鼓励“Agent 越多越好”。它不是在开会凑人数。它更像给复杂任务一个可降级、可接管、可审计的组织框架。

## Slide 19 多 Agent 模式

常见多 Agent 架构大概有三类。

第一类是单点 Supervisor。优点是简单、可控、容易理解；缺点是主控容易成为瓶颈。

第二类是 Mesh 网络型。Agent 之间可以互相调用。优点是灵活；缺点是权限、循环、追责和调试成本会快速上升。

Mesh 最怕变成一个巨大的“我已同步”网络。

“这个我同步过了”是协作系统里最神奇的一句话。同步过不等于负责过，转发过不等于解决过。Agent 之间如果只会 handoff，没有 owner 和 trace，最后也会变成一张巨大的“我已同步”网络。

第三类是 Workflow 或 DAG。状态机清晰，适合确定路径；但对于开放目标，需要额外治理对象。

三省六部的选择是混合：治理层保持星型收敛，执行层按任务临时展开，并且受工具清单、handoff 白名单和停止条件约束。

## Slide 20 治理星型 + 执行网络

治理星型负责收敛。太子分拣，中书成案，门下审议，尚书派发。这些节点不一定都是模型，但它们保证任务进入统一治理链。

执行网络负责灵活。六部可以按能力调用不同工具，比如浏览器、终端、文件、仓库、PPT、表格。不同任务可以展开不同执行路径。

这里的关键是：灵活不等于自由互调。执行层可以灵活，但要在治理层给出的范围内灵活。

我不是说项目经理能解决一切问题，但没有边界的时候，系统就会进入一种神秘状态：每个人都在推进，每件事都在进行，但没有任何东西真的结束。

Agent 系统也一样，终止条件和责任边界比热闹重要。

## Slide 21 四个工程问题

这里把一些常见 Agent 面试题，换成工程题。

第一，Workflow 和 Agent 的区别是什么？Workflow 是路径明确，Agent 是路径动态。企业落地时不能只问“能不能自动”，还要问“哪些部分应该固定，哪些部分允许动态”。

第二，能不能把几十个工具全给 Agent？技术上可以，工程上最好别。工具越多，选择空间越大，错误面也越大。

这就像新人第一天入职，你不能因为他很聪明，就把所有系统权限、生产库密码、财务审批和发布按钮都给他。不是不信任人，是制度不应该考验人性。Agent 也是一样，不应该靠“它应该不会乱点”来做安全设计。

第三，Multi-Agent 怎么连接？可以 supervisor，可以 handoff，可以 agents-as-tools，也可以 workflow。三省六部的做法是治理收敛、执行展开。

第四，如何确认 Agent 真完成了任务？不能只看它说“我完成了”。要看证据链：状态、工具、文件、测试、产物、审批、回奏。

这四个问题串起来，就是三省六部从“有趣隐喻”走向“工程控制面”的原因。

---

## Slide 22 企业担心的不是模型不聪明

很多时候，企业不是觉得模型不聪明。恰恰相反，模型越来越聪明以后，大家更谨慎了。因为它真的能做事。

一个不会动手的模型，最多答错；一个能动手的 Agent，可能改错文件、发错消息、跑错命令、泄露敏感信息、消耗大量成本，还可能留下没人说得清的过程。

这就是企业 IT 部门谨慎的原因。不是保守，而是负责。

很多业务同学会觉得 IT 审批慢，但从 IT 的视角看，很多“帮我开一下权限”背后都可能是一个未来的事故复盘。

审批不是为了制造痛苦，虽然它有时候确实很像在制造痛苦；审批的本质是避免大家在周五晚上一起制造更大的痛苦。

如果 Agent 要进入真实工作流，它必须回答：权限怎么控制，数据怎么保护，失败怎么追责，变更怎么回滚，结果怎么验收。

三省六部要解决的正是这个问题：不是让 Agent 更像人，而是让 Agent 更像一个受控的生产系统。

## Slide 23 企业风险

这一页列的是企业视角真正担心的东西。

权限越界：它能不能访问不该访问的系统？能不能执行不该执行的命令？

数据泄露：提示词、工具输入输出、日志里是否包含敏感数据？Trace 要不要脱敏？

质量不可验证：它说完成了，怎么证明真的完成？

回滚与追责：做错了，能不能知道哪一步做错、谁批准、怎么恢复？

成本不可控：模型调用、工具调用、重试、超时，怎么限制？

这些都不是靠一句 Prompt “请你小心一点”能解决的。Prompt 可以表达愿望，但不能承担制度。制度要落到执行层。

“请你小心一点”在工程里不是安全策略，最多算一句祝福。就像公司门口贴一个“请大家不要越权”，它不能替代门禁系统。

所以后面三页其实是对应关系：Policy 先拦，Isolation 先隔离，Evidence 负责复盘。

---

## Slide 24 Policy Gate

这就是门下省的工程意义：权限不能只写在 Prompt 里，必须写进执行层。

在新版里，Policy Gate 的输入不是自由文本，而是结构化 RunSpec、tool allowlist、scope、risk、approval 和 evidence_required。

比如任务里出现 shell.command，或者包含删除、覆盖、reset、生产环境、密钥这类词，就会被评为高风险。高风险任务不会直接自动执行，而是进入审议或审批。

这里也回答一个可能的问题：它为什么判断得这么快？是不是模型判断？

当前版本主要是规则和能力配置推断，不是每次都调用大模型判断。也就是说，它现在更像一个可解释的策略原型：关键词、能力、资源范围、运行模式共同决定 Policy Gate。

优点是快、稳定、可解释；缺点是语义理解还不够深。未来要把它升级成更完整的 policy engine。

更重要的是，RunSpec 不是唯一裁判。RunSpec 是输入之一，真正执行前还要按 capability、resource、action 做二次校验。即使前面的意图识别漏了，Runtime 前置校验仍然要兜底，风险处理取高不取低。

这里我会坦诚一点：现在它不是神谕，是规则。规则不丢人，不可解释的神谕才吓人。

## Slide 25 隔离等级

真实案例之前，先讲生产任务的隔离。

当 Agent 开始改代码或文档时，不能默认“直接改”。尤其在企业里，直接改生产资源是高风险动作。

这和公司权限分级很像。不是说某个人能力不行，而是钥匙不能随便发。你不能因为一个人 Excel 用得好，就顺手给他生产发布权限。能力和权限是两回事。

所以我把任务分成 L0 到 L3。

L0 是只读，比如问答、检索、日志摘要。这里要强调，L0 到 L3 是风险等级，不是能力等级。

L1 是产物可审，比如生成 PPT、Word、报告，先产出文件，再由人确认。

L2 是 Patch-first，比如代码修改，先形成 diff 或 patch，再审批合入。

L3 是审批执行，比如删除、发布、生产操作，必须人工确认、隔离执行、可回滚。

三省六部未来要做到的是：越接近真实资源，越要从相信模型切换为隔离执行和人工放行。

## Slide 26 真实案例一：RunSpec

下面用一个真实案例讲新版三省六部怎么运行。

这次输入的需求是：分析当前三省六部本地运行数据，输出一页演示用运行诊断，包括任务数量、RunSpec、Policy Gate、Runtime Outbox、模型观测和下一步改进建议，只读，不修改仓库。

如果直接进入执行型 Agent，它可能会很快开始读文件、跑命令、总结。这个能力很强，但企业场景里还要先问：它要读什么？会不会写？风险多高？有没有产物？能不能复盘？

在三省六部里，它先进入 RunSpec Preview。系统先识别目标类型、目标部门、能力集合、风险等级和执行图。

这一步有点像需求进来以后，先不要让研发直接开干。先问一句：这是需求、故障、咨询，还是临时追加的紧急方向？不同类型，处理方式完全不一样。

很多 AI 需求的开头都是一句非常朴素的话：这个能不能让 AI 做？这句话本身不是需求，它是一个需求宇宙的入口。真正的问题不是能不能让 AI 做，而是让它做什么、做到哪里、能不能停、错了谁接。

第二步，看板把运行状态放到同一张图上。

这页是本地开发环境的单次快照。可以看到任务、队列、治理链路、责任部门和关键数量。这里的关键不是数字本身，而是口径。

以前我自己也容易犯一个错误：看到一个很大的数字，就想放进 PPT。后来发现字节这样的听众一定会问：时间窗是什么？分母是什么？是否去重？是当前快照还是累计？

这个职业病非常好，它会逼着系统诚实。

## Slide 28 真实案例三：证据可读

第三步，是这次新版面板里我最想强调的执行记录。

旧版的问题是信息容易混在一起：flow_log、progress、tool_result、模型状态、产物文件都挤在任务详情里。看起来什么都有，但人很难一眼知道重点。

新版做了一个执行叙事层。它先告诉你任务处于什么状态，下一步该看什么；然后把判断路径、最近动作、执行回顾、子任务、Trace 和动态记录放在同一个 task 下面。

这一步非常关键。真正的可观测性不是“日志越多越好”。

日志太多就像把一个人丢进档案室，然后告诉他“证据都在这里”。这不叫可观测，这叫考古。

很多系统都有这个问题：日志确实全在，但你找不到。就像公司知识库，文档确实都有，但搜索结果第一页是 2021 年的制度，第二页是离职同事的草稿，第三页才是你真正想看的。

证据链不是把所有东西堆起来，而是让人能沿着关键线索走下去。

所以案例结论是：三省六部不是替代 OpenCode，而是把一次会话提升为可追踪、可审议、可接管的生产任务。

## Slide 29 V1 vs v30：先给估算口径，再谈价值

这一页是 v30 里非常重要的修正。

前面三页案例说明的是：对象闭环已经存在。也就是说，RunSpec、Policy、Queue、Trace、Evidence 这些对象已经能串起来。

但这还不能直接证明“三省六部一定比直接用执行型 Agent 更好”。一个 demo 只能证明系统跑起来了，不能证明它已经有生产价值。

所以这一页我先给估算口径，而且明确写清楚：这是本地开发和复盘口径，不是生产 SLA。

比如 V1 看板期，卡点定位可能要在三到五个地方人工翻日志、翻文件、翻状态；v30 控制面原型希望把它收敛到一个任务详情入口，task、queue、trace 同屏。下一步目标是主堵点两分钟内定位。

证据完整度也是一样。V1 时 flow、progress、tool 分散；v30 希望 RunSpec、Policy、Trace、Artifact 同链。下一步要用 evidence completeness 这种指标去衡量，而不是只靠“感觉更清楚”。

模型状态过去容易出现 OpenCode 和平台状态不一致；现在目标是注册表、latency、failure、fallback 能统一观测。

接管触发过去更偏事后发现问题；现在要让 risk、timeout、no-evidence 这些条件触发预览或人工接管。

这页还把 61 道旨意、13 条 RunSpec、350 条 Runtime Outbox 做成一个小图表。这里仍然强调：它是本地开发环境单次快照，不代表生产规模。

这也是我这次改版后更清醒的一点：工程化不是多画几个框，而是这些框最后能不能变成运营指标。

## Slide 30 回到未来：个人 PC 会变成 Agent 工作场

不管我们把它叫 AI PC、Agent Workbench，还是个人智能工作站，趋势都很清楚：个人电脑不再只是人打开应用的设备，而会变成 Agent 可以受控使用的工作场。

以前电脑是“人用应用”。未来可能是“Agent 受控地使用应用、文件、网页、命令行和办公套件”。

如果这个趋势成立，那么控制面会更重要。因为本地电脑里有文件、浏览器登录态、代码仓库、办公文档、终端命令，这些都是高价值资源，也都是高风险资源。

个人电脑其实很像一个小型公司：里面有财务材料、有项目资料、有历史聊天记录，还有一堆你自己都忘了为什么存在的文件夹。

让 Agent 进来操作，不是请了个秘书那么简单，更像请了一个会用所有工具的新同事。新同事再聪明，也要先讲清楚边界。

## Slide 31 AI PC 里的控制面

这里不能只讲愿景，必须落到一个具体判断：AI PC 应该是受控 Runtime。

本地文件、网页、命令、PPT、代码仓库都会变成工具。Agent 调工具之前，需要 Permission Broker；执行之前，需要 Policy Gate；执行之中，需要 Monitoring；执行之后，需要 Evidence 和 Evals；不确定时，需要 Human-in-the-loop。

所以三省六部要做的不是替用户按按钮。替用户按按钮只是自动化；让 Agent 在真实资源中受控行动，才是工程化。

这里我也不会说三省六部已经全部实现。更准确的说法是：这次大改版正在把这些对象逐步落地。

## Slide 32 路线图：按指标收敛六个闭环

下一步最现实的不是继续加概念，而是按指标收敛六个闭环。

概念很容易让人兴奋，闭环很容易让人清醒。做开源项目的时候，前一天觉得自己在重新定义未来，第二天发现本地服务又起不来了。未来很宏大，报错很具体。

P0 先打通模型路由与 Trace。

模型路由要让 OpenCode 已配置模型同步到平台侧注册表，延迟、超时、failover 和等级降级都可观测。

事件与 Trace 要让 run、agent、handoff、tool、artifact span 扣到同一条证据链上。

P1 要同步收敛 Policy、Isolation 和 Evals。这里我把 Evals 提前了，因为如果没有评估，控制面就很容易变成“看起来很完整”的架构图。

Policy Gate 要让 tool allowlist、审批人、scope、expiry 都进入执行层约束。

任务隔离要做到一任务一上下文、patch-first、可审可回滚。

终止与接管要把 max_turns、timeout、重复失败、handoff_to_user 变成系统级 stop condition。

Evals 与 SLO 要看失败样本回流、policy FN/FP、evidence completeness 和在线回归指标。

没有评测的架构图，就像没有单元测试的豪言壮语：PPT 上都很稳，一跑全是边界条件。

没有评测的架构图，就像没有单元测试的豪言壮语：PPT 上都很稳，一跑全是边界条件。

所以六个闭环做扎实，三省六部才可能从一个好玩的开源项目，变成真正能支撑工程试点的 Agent Workbench。

## Slide 34 抛砖引玉：三个问题留给现场

这一页是互动页。

我不希望这场分享变成我单向讲完，而是希望把三省六部当成一个讨论样本。

第一个问题：你们的 Agent 目前在“信任”上卡在哪里？是权限、数据、质量，还是责任边界？

第二个问题：什么场景下你会选择“信任 Agent 直接执行”，而不是让它先进入人工审批？这个分界线非常关键。

第三个问题：如果你的公司要上 Agent 控制面，第一步应该做什么？是模型路由，是工具权限，是 evidence ledger，还是先做只读诊断任务？

这三个问题，其实比“哪个模型最强”更接近企业落地。模型会继续变强，但组织敢不敢放权，取决于这些控制面能力能不能站住。

讨论可以继续，但最后我先把今天的核心判断收束成一句话。
## Slide 35 收束

最后回到这三个问题：Trust、Monitor、Takeover。

Trust：信任依据是什么？不是“模型说它完成了”，而是 trace、tool、artifact、policy、review 都能对上。

Monitor：如何定位卡点？不是刷新页面祈祷，而是看到模型、队列、session、policy、worker 哪一层在堵。

Takeover：何时触发接管？不是等出事故，而是在高风险、超时、无证据、越权、失败重试时触发人工介入。

如果这三个问题回答不了，模型能力越强，系统风险也会越大。

所以今天分享的核心不是“我做了一个历史风格的 Agent 面板”，而是：当 Agent 进入真实工具、真实文件、真实业务流程之后，我们需要一个能让人信任、能被监控、能随时接管的控制面。

最后用一句不太严肃的话收一下：以前我们担心 AI 不够聪明，现在慢慢开始担心它太能干。一个不能干的系统最多让人失望，一个太能干但没有边界的系统，可能让大家周五晚上开事故复盘。

所以三省六部想解决的，不是让 Agent 看起来更热闹，而是让它真的进入工作流以后，不把大家的周末变成事故复盘。

如果今天只记住一句话，我希望是这一句：Agent 进入真实资源之后，能干活只是开始，敢放权才是生产化。

最后也欢迎大家拍砖。尤其是字节的同学，在企业 IT、平台工程和大模型落地上经验非常丰富，我更希望这次不是我讲完就结束，而是把三省六部当成一个讨论样本：什么地方可取，什么地方还不成熟，什么地方需要继续被真实生产环境验证。

# 附：可以临场插入的短梗库

1. **RunSpec 梗**：用户说“优化一下系统”，系统听完以后说：你这是需求，还是许愿？
2. **审批梗**：审批不是反派，审批是为了大家不要周五晚上一起当主角。
3. **日志梗**：日志都有，不等于证据可读；资料都在知识库里，也不等于人类找得到。
4. **多 Agent 梗**：不是 Agent 越多越聪明，有时候只是“六个模型一起想不明白”。
5. **AI 需求梗**：很多 AI 需求不是一句需求，而是一个需求宇宙的入口。
6. **证据梗**：最终版、最终版2、最终版_真的最终版，本质上是人类社会对 artifact versioning 的朴素探索。
7. **队列梗**：pending age 一上来，看起来是 AI 不努力，其实是队列、权限、工具和上下文一起把它压垮。
8. **收束梗**：能干活让人兴奋，能留证、可接管，才配进入工作流。
